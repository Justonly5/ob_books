
先理解几个内存指标

```
RSS（Resident Set Size）：
  进程实际占用的物理内存
  包含：堆、栈、代码段、JVM 自身、Native 内存
  不包含：已 swap 出去的内存

WSS（Working Set Size）：
  K8s 里实际用的是 container_memory_working_set_bytes
  = RSS - 可回收的文件缓存（inactive file cache）
  这是 K8s OOM Killer 判断内存使用的核心指标

container_memory_usage_bytes：
  包含所有缓存，通常比 WSS 大
  不是 OOM 判断依据
```


### Full GC 后指标会下降吗

**RSS 和 WSS 大概率不会立即下降**，这是最核心的结论。

原因在于 JVM 和操作系统对内存的处理方式不同：

```
Full GC 做了什么：
  扫描堆，标记存活对象
  回收不可达对象占用的堆空间
  → 堆内部的 used 下降了（比如从 14G 降到 4G）
  → 但这 10G 内存 JVM 并没有还给操作系统
  → 只是在 JVM 内部标记为「空闲可复用」

操作系统视角：
  这 10G 的物理内存页还映射在进程地址空间
  RSS 没有变化，还是 14.5G 左右
  WSS 同样没有变化
```

##  jvm 启动的时候 设置 xms=xmx=14G RSS WSS 会是多少

这是一个很关键的问题，涉及 JVM 内存分配的实际行为。

### 核心结论：启动时 RSS/WSS 不会立即是 14G

这是最常见的误解。`-Xms=14G` 并不意味着 JVM 启动时就向 OS 申请了 14G 的物理内存。

---

### 两个层面的内存分配

```
JVM 向 OS 申请虚拟地址空间（mmap/VirtualAlloc）
  → 立即完成，14G 的虚拟地址空间被预留
  → VSZ（虚拟内存）立刻显示 14G+

OS 实际分配物理内存页（缺页中断）
  → 不是立即分配
  → 只有 JVM 真正写入数据时才触发缺页中断
  → OS 才把物理内存页映射进来
  → RSS/WSS 随着实际使用量逐步增长
```

这是 Linux 的 **Lazy Allocation（延迟分配）** 机制，也叫 **Demand Paging**。

Linux 的内存分配是两步走：

```
第一步：mmap 申请虚拟地址空间
  → 只是在进程的地址空间里划一块区域
  → 没有对应的物理内存页
  → 这块区域读写会触发缺页中断

第二步：真正写入数据时触发缺页中断
  → OS 才分配物理内存页
  → 建立虚拟地址 → 物理地址的映射
  → 这个物理页才计入 RSS
```
