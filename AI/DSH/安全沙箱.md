Sandbox 的目标不是阻止 Agent 修改工作目录，而是把 Agent 的"能力边界"限制在工作目录及允许的资源范围内。
Agent 仍然可以修改挂载目录中的文件；Sandbox 主要限制的是 Agent “怎么执行”和“还能碰哪些东西”，而不是自动阻止它修改被授权挂载的目录。

**Agent 的“沙箱模式（Sandbox Mode）”本质上是给 Agent 提供一个受隔离、受限制的执行环境**，让 Agent 可以执行 Shell、Python、安装依赖、读写文件、运行 Git、启动服务等操作，但即使 Agent 被提示词攻击、工具调用出错或者生成了恶意命令，也尽量不会影响宿主机和其他系统。

Sandbox 并不等于 Docker，SandBox 是一个**安全隔离模型**。而 Docker 是实现隔离的一种技术。

## 增强功能

### execd 进程
最核心的增强是——**每个沙箱 Pod 里都注入了 `execd`**（用 Go 写的守护进程，端口 `44772`），它是客户端唯一对话的对象：

- **命令执行**：shell 语法 / 直接 argv 两种形式，支持 SSE 流式输出、后台命令 + 状态轮询 + 增量日志（后台日志可保留 24h）。
- **文件系统 API**：上传、下载、列目录、移动、删除——"沙箱文件系统完全可脚本化"。
- **代码执行**：Jupyter-backed 的代码上下文（Code Interpreter 内核，Python/Java/Node/Go）。
- **交互式终端（PTY）**：WebSocket 真终端，且支持"1 个 holder 持键盘 + N 个 viewer 围观"的共享模型。
- **资源指标**：CPU/内存快照 + 实时流，OpenTelemetry 导出。
- **生命周期钩子**：`preStart`（入口启动前必须成功的初始化）、`periodic`（定时任务），在 execd 里执行。
- **execd-as-init**：作为 PID 1 收孤儿进程、转发信号、传播退出码——让沙箱状态能反映进程真实做了什么。

**对比裸 Pod**：你建一个 `kubectl run ubuntu`，是没有 execd 的，只能 `kubectl exec` 进容器手敲命令、`kubectl cp` 拷文件。OpenSandbox 把这些操作封装成一套 **Agent 友好的 HTTP API**（有流式输出、可轮询的 Execution 对象、文件/代码/终端语义），并且 execd 是每个沙箱标配，SDK 一层薄封装即可调用。

### 


|能力|裸 K8s Pod|OpenSandbox 沙箱|
|---|---|---|
|命令/文件/代码/终端执行|`kubectl exec` / `cp`，手工|execd HTTP API，流式、可轮询、Agent 友好|
|状态查询|`kubectl describe`|lifecycle API + `SandboxSnapshot` CR|
|暂停/恢复|❌ 无|rootfs commit→OCI 镜像→registry→释放资源→用快照重建，`sandboxId` 稳定|
|预预热快速分配|❌ 无（走调度）|Pool 认领 warm pod，0.92s/100 个|
|出向网络策略|需自配 NetworkPolicy|内置 egress sidecar + DNS/nftables + Credential Vault|
|多租户|需自建|API Key → namespace 自动路由|
|统一跨后端 API|❌|同一 lifecycle API 覆盖 Docker/K8s|
|生命周期钩子/定时任务|❌ 无|preStart / periodic|
